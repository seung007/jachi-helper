# 대화 데이터로 다시 판단한 자취도우미의 제품 방향

> 필요시 읽는 당시 근거/검토 기록이다. 최신 상태는 [현재 작업](current-work.md), 방향·실행 규칙은 [제품 방향](product-vision.md)과 [AGENTS](../AGENTS.md)를 따른다. 아래 제안·실험 문턱·당시 승인·집계는 현재 명령이나 새 작업의 승인으로 재사용하지 않는다.

작성일: 2026-09-26. 현재 로컬 코드와 사용자 제공 대화 자료를 분석했다. 실제 운영 배포 화면이나 전환 성과를 확인한 보고서는 아니다. 아래 우선순위는 제안이며 사용자 확정 결정으로 기록하지 않는다.

## 결론

기존의 '주거 생활 실행 시스템' 방향을 유지하되, 홈과 결과가 사용자의 질문에서 시작해 다음 행동까지 이어지도록 바꾸는 것이 핵심이다. 현재 39개 품목을 보여 주는 화면은 물건 이름을 아는 사용자에게는 도움이 되지만, '직접 청소할까', '누구에게 어떻게 물어볼까', '이 조건에서 어떤 제품이 맞을까'에는 답이 부족하다.

지난 답변에서 이불을 최우선으로 단정한 것은 구현하기 쉬운 사례를 전체 전략의 우선순위로 확대한 판단이었다. 이불은 유효한 첫 구매 선택 사례다. 그러나 서비스 연결이라는 제품 목표를 함께 검증하려면 입주청소의 직접 처리/업체 이용 판단도 필요하다. 두 사례에 공통으로 쓰는 작은 의사결정 흐름을 만들고 기존 홈과 준비표에 연결하는 것을 제안한다.

## 이번에 확인한 데이터

- 원본: 사용자가 제공한 `자취.txt`, 2026-06-25~09-23. SHA-256이 기존 데이터셋의 `8f5d54b6092459aad50409ad3436b8815f705e2d494a4f391c3797c48996a81a`와 일치한다.
- 기존 파싱: 159,120개 메시지, 자동 질문 후보 6,645개, 기존 6개 주제에 걸린 후보 946개. 이 수치는 파싱/키워드 검색 결과다.
- 기존 수동 검토 메시지 ID 17개를 제외한 929개에서, 고정 seed와 메시지 ID의 해시 순으로 48개를 추출해 발언을 검토했다. 21개는 앞뒤 대화도 확인했다. 과거에 본 대화와 같은 사건의 다른 발언이 포함돼 있다.
- 48개 중 직접 필요·선택 질문으로 분류한 발언은 19개, 상황을 덧붙인 발언은 9개였다. 나머지에도 도움을 주는 사람의 추가 질문 3개, 경험 서술 2개 등 제품 설계에 쓸 정보가 있었다. 19개를 독립 문제나 사람 19명으로 해석하지 않는다.
- 질문 인덱스에서 빠진 발언 12개와 주제 태그가 없는 발언 12개를 별도 검색 표본으로 읽었다. 식사·식비와 짧게 나눠 쓴 질문의 누락을 확인했다.
- 원문은 공개 자료로 옮기지 않았다. 아래 근거는 비공개 데이터셋의 메시지 ID와 원본 줄 위치로 추적한다.

비공개 검토 자료:

- `data/exports/chat-research-8f5d54b60924/reassessment-2026-09-26/review-ledger.jsonl`: 48개 발언의 수동 분류·이유·문맥 확인 여부.
- `review-evidence.json`: 위 기록에 원본 날짜와 줄 번호를 연결한 결과.
- `review-summary.json`: 표본 크기와 분류 집계. `verify-review.mjs`로 표본 선택, ID 일치, 중복 여부를 재검증할 수 있다.
- `coverage-audit.json`: 누락과 오탐 점검 방법 및 추가 24개 발언의 ID.

## 이전 분석에서 수정할 점

1. 기존 r005(m036278, 원본 37812행)는 반복 질문을 흉내 내는 대화 안에 있었다. 직접적인 건조기 구매 고민으로 분류한 것을 철회하고 레코드와 이전 문서를 정정했다. 실제 원룸 건조기 설치/빨래방 질문은 별도 사례 m115314~m115320에서 확인된다.
2. 15자 미만을 제외하는 필터는 짧은 밥솥·반찬 질문을 누락했다. '서랍장에서...' 뒤에 냄새 제거 질문을 이어 쓰는 사례도 메시지 하나씩 읽으면 의미가 끊긴다.
3. '청소'가 들어간 닉네임 호출, 고용 계약 질문, 상품 공유 문구와 수요조사 모집글을 개인의 생활 문제로 세면 빈도가 왜곡된다.
4. 현재 6개 주제는 기존 사이트의 범위에 가깝다. 식사·장보기 같은 주제가 빠지므로 이 분류표로 자취 생활 전체의 문제 순위를 매길 수 없다.
5. 사이트에서 정보를 얻은 뒤 구매·예약했는지는 이 자료로 확인할 수 없다. 다만 대화 안에서 제품 후보를 찾았다고 말하는 수준의 진전은 구별해 기록할 수 있다(m102954~m102957).

## 기능 우선순위 제안

숫자 가중치는 사용하지 않았다. 확인한 문제와의 직접성, 기존 제품 목표와의 연결, 현재 코드 재사용, 외부 데이터·연동 없이 제공 가능한 결과를 기준으로 판단했다. 대화 빈도 순위가 아니다.

| 순서 | 작업 | 이 순서인 이유 | 완료된 사용자 결과 |
| --- | --- | --- | --- |
| 1 | 홈의 상황 선택과 작은 공통 결정 흐름. 첫 사례는 입주청소와 이불. | 기존 서비스·품목을 재사용하면서 '조건을 한 번 받고 다음 행동으로 연결'하는 제품 약속을 함께 시험한다. | 이용자가 자신의 조건에 맞는 선택지와 다음 행동을 얻는다. |
| 2 | 서비스 문의 준비와 선택 이력 연결 | 대화에서 연락 부담과 비교 조건 부족이 확인됐다. 예약 API 전에 제공할 수 있는 가치다. | 작업 범위·확인할 정보·중립적 문의 초안이 준비되고 진행 상황이 남는다. |
| 3 | 세탁·수납 등 품목별 조건 확장 | 기존 세제 비교와 39개 품목 기반을 활용할 수 있다. | 사용 목적과 집 조건으로 후보를 줄이고 선택 이유를 다시 확인한다. |
| 4 | 입주 후 문제 대응 | 재방문 후보지만 안내의 정확성과 후속 책임이 더 중요하다. | 검증된 초기 확인 정보, 연락 대상, 해결 여부를 이어 본다. |
| 보류 | 계약 판단 자동화, 전 품목 실시간 최저가, 할인 알림, 전체 생활 분야 확장 | 개인별 판단·외부 데이터·운영 범위가 크게 늘어난다. 이번 대화만으로 이 기능들의 우선순위를 확정할 수 없다. | 관련 근거와 운영 준비를 갖춘 뒤 별도 범위를 정한다. |

서비스 연결과 상품 추천은 선택한 상황에 따라 갈라지는 결과다. 모든 사례를 구매 링크로 끝내거나 모든 문제에 '필요함/이미 있음/나중에' 상태를 강제하지 않는다. 상품은 후보/보유, 문의는 준비/연락/응답 대기, 문제는 미해결/해결처럼 실제 다음 행동을 표현한다. 상태 수는 해당 화면에 필요한 최소한으로 제한한다.

## 첫 구현을 검토할 수 있는 구체안

공통 흐름: `상황 선택 -> 필요한 조건 2~3개 -> 가능한 선택과 이유 -> 다음 행동 -> 이어보기`.

### 입주청소

- 진입 질문: 직접 청소할지 맡길지 고민 중인지, 이미 업체를 찾는 중인지.
- 필요한 입력: 공간 규모, 눈에 보이는 오염과 필요한 작업 범위, 직접 할 시간·의향. 전문 확인이 필요한 상태는 별도 분기한다.
- 결과: 직접 처리할 경우의 작업 범위와, 견적을 요청할 경우 빠뜨리지 않을 조건을 나란히 제공한다. 추정 견적이나 품질 보증을 만들지 않는다.
- 다음 행동: 선택에 따라 작업 목록 또는 업체의 견적 경로로 연결한다. 전달 자료와 중립적인 문의문은 보조 수단이며 실제 요청 전송 여부를 명확히 구분한다.
- 완료 판단: 사용자가 직접 처리/견적 문의/추가 확인 중 다음 행동을 정했는지 확인한다. 업체 링크를 눌렀다고 예약 완료로 저장하지 않는다.

### 이불

- 진입 질문: 당장 사용할 침구가 있는지, 새로 사야 하는지.
- 필요한 입력: 사용할 크기, 세탁·건조 환경, 관리 방식과 예산 우선순위. 예산은 해당 구매의 범위로만 사용한다.
- 결과: 관리 방식별 선택지와 확인해야 할 규격을 제시한다. 세탁기 용량만으로 특정 이불의 세탁 가능성을 단정하지 않고 각 제품 표시를 확인한다.
- 다음 행동: 조건에 맞춘 제품군 탐색과 후보 저장. 실제 확인된 상품 정보가 있을 때 제품 단위 비교를 제공한다.
- 완료 판단: 사용자가 후보 또는 구매 방식을 좁혔는지 확인한다. 구매 완료는 본인의 확인과 구분한다.

## 대화 데이터를 계속 쌓는 방법

자료를 두 층으로 유지한다. 원문·시간·가명 화자·줄 번호는 비공개 보관하고, 제품에 쓰는 기록은 익명 상황·조건·결정·다음 행동·관찰된 결과로 작성한다.

검토 단위 예시:

`caseId / evidenceMessageIds / stage / trigger / constraints / decision / clarificationNeeded / proposedNextAction / observedOutcome / confidence / reviewStatus`.

같은 시간에 여러 주제가 섞이므로 시간 간격만으로 대화를 자동 병합하지 않는다. 같은 질문자의 후속 설명, 답변 내용, 주제와 시점을 함께 확인한다. 인용·농담·모집·광고형 공유·남의 경험을 별도 표시한다. 채팅의 추천 답변은 상품 효능이나 제도·수리 지침의 검증된 근거로 승격하지 않는다.

전체 자료를 바로 학습시키거나 벡터DB에 넣을 필요는 없다. 우선 선택한 두 시나리오에 필요한 검토 사례를 늘리고, 질문 문구·입력 항목·분기·결과를 이 기록에서 추적할 수 있게 연결한다. 데이터의 가치는 요약 분량보다 실제 기능의 판단 근거를 바꿀 수 있는지에 있다.

## 첫 검증에서 볼 것

- 조건 입력 뒤 선택지를 좁혔는지와 도움이 된 이유를 짧게 받는다.
- 입력 도중 이탈한 위치, 같은 정보를 반복 입력한 횟수, 다음 행동 선택을 확인한다.
- 문의 준비, 판매처 이동, 실제 예약·구매·해결을 서로 다른 결과로 기록한다.
- 성공률 목표를 이 대화에서 추정하지 않는다. 첫 사용 관찰은 기능의 막힘을 찾는 데 사용하고 재방문 증가의 증거로 확대하지 않는다.

## 적용한 스킬의 범위

`grounded`의 접지 방식으로 원문·코드·해석을 연결하고 오류를 수정했다. `ai-saas-builder`는 기존 기능을 재사용해 사용자의 다음 행동을 시험한다는 원칙만 적용했다. 이 제품은 크레딧 판매형 AI SaaS가 아니므로 스킬의 결제·유료 고객 수 기준을 그대로 제품 진행 조건으로 적용하지 않았다.
