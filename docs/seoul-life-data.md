# 서울 생활정보 수집

## 2026-10-18 실행 DB 준비

로컬 서비스 구현 상태는 current-work.md의 최신 항목을 따른다. 운영 준비로 기존 842,469,376바이트 SQLite에서 검색·표시용 10개 필드만 추출한 읽기 전용 DB를 만들었다. 554,092행/25구를 유지하고 전체 필드 값의 SHA-256, 건수, 무결성을 검증했다. 주소는 기존 검색 API와 동일하게 도로명 우선·지번 대체 값을 보존한다. 원본/원문/분류 원장은 수정하지 않는다.

- 출력: 비공개 `data/exports/life-place-runtime/manifest.json`과 해시 버전 SQLite. Git·정적 경로·Vercel 업로드 제외 유지. 재실행은 원본 해시가 같으면 재사용한다.
- 로컬 API는 이 실행 DB를 우선 읽는다. 실행 manifest가 존재하면서 손상됐으면 원본으로 조용히 전환하지 않고 503으로 표시한다.
- 측정 크기: 184,270,848바이트(약 184.3MB), 원본 대비 78.1% 감소. 원본을 브라우저 다운로드로 바꾸지 않는다.
- 2026-10-18 [Vercel 공식 함수 제한](https://vercel.com/docs/functions/limitations)의 일반 Node 번들 한도는 비압축 250MB이다. DB 단독 크기만으로 배포 성공을 보장하지 않는다. 원자료의 공개 재사용 조건·출처 표시, Node/SQLite 런타임, 함수 코드와 데이터의 실제 번들 포함·정적 노출 차단, 총 용량은 승인 후 로컬 배포 빌드로 추가 검증한다. 이번에는 외부 업로드·환경변수 변경·배포를 하지 않았다.

운영 방향은 정적 상품/서비스 화면을 유지하면서 읽기 전용 장소 API만 별도로 패키징하는 것이다. 대용량 원본 배포나 외부 유료 DB 계약을 자동으로 추가하지 않는다. 실제 번들 검증이 실패하면 최소 데이터 저장소 연결을 별도 제안하며 기존 수집 자료·전체 범위를 축소하지 않는다.

최신 구현 전 검토는 [2026-10-17 연결 설계](#대화-니즈와-앱-연결-설계-2026-10-17)를 따른다. 지역·원자료 계약은 [2026-10-16 재분석](#서울-전체-탐색-재분석-2026-10-16)을 유지한다. 10월 15일 시안은 범위/탐색 설계가 부족해 수정 대상이며, 최종 설계 승인이나 전체 연결 완료가 아니다.

2026-10-14 사용자 신규 범위: 서울 한정으로 생활 도움 사이트와 다이소·대형마트·편의점·주유소·카페·식당 등 생활 관련 업소를 먼저 전량 수집한 뒤 분류/세분화한다. 기존 상품 품목을 삭제하거나 생활 페이지를 운영 배포하라는 승인은 아니다.

- 생활 도움 공식 사이트와 보완 자료는 scripts/seoul-life-sources.mjs에서 관리한다. 본문 직접 확인·검색 색인만 확인·접근 제한을 구분한다. 공공시설 자료의 메타데이터 발견을 시설 원본 확보로 대체하지 않는다.

## 파일과 실행

로컬 자료 위치: data/exports/seoul-life-2026-10-14/. Git·운영 배포·로컬 공개 서버 입력으로 자동 사용하지 않는다.

## 분류 계약

- 사용자용 분류/이용 목적은 규칙 기반 제안이다. 공식 원본 분류를 덮어쓰거나 업소가 실제 제공하는 서비스/재고로 승격하지 않는다. 소분류 코드 전체를 한 번씩 연결한다. 새 업종은 삭제하지 않고 검토 대기로 보존한다.
- 일반 카페와 독서실/스터디카페, 사람 의료기관과 동물병원, 약국과 병원, 주유소와 가정용 연료, 이마트와 이마트24를 구분한다. 구역은 원본의 행정동/법정동 코드·이름을 분리한다. 원본 구역 수를 현재 행정구역의 공식 총수로 일반화하지 않는다.
- 이름 기반 브랜드 후보는 미검증이다. 원본 업종과 이름이 모두 맞을 때만 후보로 기록하며, 후보가 없다고 독립점/비가맹점이라 판정하지 않는다. 공식 다이소 소스는 별도 테이블로 유지하며 합산·자동 병합하지 않는다.
- 가격·주차·24시간·영업 중·리뷰·재고를 이름이나 업종으로 생성하지 않는다. 상세 속성 파일은 미확인을 false/0으로 바꾸지 않고 출처별 결손을 보여 준다.
- 결과: classification/taxonomy.md·json, area-index.json, brand-candidates.json, helpful-sites-classified.json, attribute-coverage.json, inventory-corrections.json, classification-report.json 및 로컬 SQLite. 전체 원본 payload는 그대로 보존한다. 로컬 SQLite는 Node 24.15.0에서 확인한 내장 도구이며 운영 API/DB가 아니다.

예시(현재 영업/실시간 검색을 뜻하지 않음):

```powershell
npm run query:seoul-life -- --district=마포구 --dong=연남동 --dong-type=legal --category=cafes-work --leaf-code=I21201 --limit=5
npm run query:seoul-life -- --source=daiso --district=강남구 --limit=5
```

동 검색에는 구를 함께 지정하며 dong-type은 legal/administrative로 명시한다. 공식 다이소에는 동 코드가 없으므로 동 코드 검색을 지원한다고 주장하지 않는다. CLI는 읽기 전용이고 가격/인기/추천순으로 정렬하지 않는다. 큰 SQLite를 일반 작업마다 재생성하지 않고 관련 분류 변경 때만 생성·검증한다.

### 지역 선택과 긴 목록

1. 첫 진입부터 `서울 전체 → 구 전체/25개 구 → 동 전체/동 검색`을 제공한다. 구를 선택하면 해당 구의 동만 표시한다. 동을 반드시 고르게 하지 않고 구 전체 검색도 허용한다. 최근 지역은 저장 동의/기존 정책 범위에서 복원하며 처음 온 사용자를 임의의 동에 배정하지 않는다.
2. 장소 탐색의 기본 동 목록은 주소에 쓰는 법정동을 기준으로 제안한다. 행정동 이름도 검색할 수 있게 하되 `역삼1동(행정동)`처럼 구분하고 그 코드를 조회한다. 행정동과 법정동을 1:1 별칭으로 합치지 않는다. 공공지원의 관할 지역도 별도 확인한다.
3. 지역 마스터는 업소 테이블과 분리한다. 공식 유효 지역은 업소 자료가 0건이어도 선택할 수 있어야 한다. `확인된 자료 없음`과 `그 지역에 실제 시설 없음`은 다르다. 구/동 코드의 변경·폐지·기준일을 보존한다.
4. 지역·분류·검색어는 화면 위에 유지한다. 긴 가로 칩 줄과 안쪽 스크롤 막대 대신 검색 가능한 선택창, 줄바꿈되는 분류 목록, 필터 요약을 사용한다. 장소와 서비스 화면은 같은 선택 지역을 공유한다.
5. 최초에는 모든 업소를 펼치지 않는다. 생활 목적을 고르는 분류 화면과 검색창을 제공하고, 전체 결과가 필요한 사용자는 `전체 결과`로 들어간다. 기본 바로가기 8개와 전체 분류 접근을 제안하되 범위를 8개로 자르지 않는다.
6. 결과는 우선 페이지당 12개, 상·하단 `이전/다음`과 `1–12 / 자료 N건` 표시를 제안한다. 무한 자동 로딩은 하지 않는다. 검색·분류·페이지·스크롤 위치를 돌아가기/외부 이동 후 복원한다. 12는 검토용 UI 값이지 연구로 입증된 최적 수가 아니다.
7. 선택한 구·동·분류의 결과만 보여 준다. 인접 지역 확대는 결과가 없을 때 사용자가 선택하며 서울 전체로 몰래 바꾸지 않는다. 동일 분류 내 다중 선택은 OR, 지역·분류·속성 간에는 AND로 정의한다.
8. 기본 정렬은 가나다순/검색 일치도처럼 설명 가능한 값으로 한다. GPS 동의 없는 가까운 순, 자료 없는 영업 중·인기순·최저가는 만들지 않는다. 좌표 기반 거리도 도보 시간과 구분한다.
9. 모바일은 한 열의 짧은 결과 행, 큰 화면은 밀도 있는 목록과 선택 상세 영역을 제안한다. 지도는 선택 도구로 두고 지도 SDK가 실패해도 목록을 이용하게 한다. 본문 16px 기준, 44px 조작 영역, 긴 이름 줄바꿈, 키보드·초점·확대 접근성을 확인한다.

### 제품 방향과 분류 연결

### 화면과 행동

기존 코드를 확장하며 대표 흐름 확인 후 같은 구성으로 전 범위에 적용한다. 사이트 전체를 다시 만드는 작업은 포함하지 않는다.

```text
상품 홈: 기존 검색 + 품목 탐색 + 생활 문제 바로가기
  → 상품 상세/비교: 차이·조건·사용/관리 정보·구매처
  → 관련 일: 직접 관리 / 근처 장소 / 맡길 서비스

생활 서비스: 문제 검색 + 전체 목적 + 필요한 지역
  → 세부 목적 선택 → 12개 결과 → 조건 확인 → 공식 웹/앱
  → 돌아오면 검색·목적·지역·페이지·스크롤 복원
```

- 홈 검색은 기존 상품 검색을 유지한다. 서비스 검색이나 우리동네로 갈 때 명시적인 목적 전환을 제공한다. 전환 후 다른 종류의 결과로 조용히 바꾸지 않는다.
- 생활 문제 바로가기는 첫 묶음의 대표 상황부터 제공하되 `전체 목적`으로 18목적/106세부 목적에 도달할 수 있게 한다. 106개를 첫 화면에 한꺼번에 펼치지 않는다.
- 서비스 검색은 앱 이름·별칭·문제 표현·확인된 기능을 검색한다. `빨래 냄새`는 사용법/세탁 경로를, `이불 수거`는 품목 접수와 수거 조건을 확인하는 경로를 우선한다. 효능·수거 가능을 문제어 매칭만으로 확정하지 않는다.
- 목적 선택 후 해당 세부 목적만 제공한다. 0건이면 `아직 확인된 연결 없음`과 목적/지역 변경을 제공하고 전체 큐에는 남긴다. 선택한 분류를 임의로 변경하지 않는다.
- 지역은 서울 전체→25구→선택적 동 검색을 재사용한다. 법정동/행정동 코드를 구분하고 0건 지역도 선택 가능하게 한다. 전국 온라인 서비스는 지역 선택을 요구하지 않는다.
- 주소별 제공 여부가 미확인인 방문/배송 서비스는 `공식 사이트에서 주소 확인`을 보여 준다. 구/동으로 확정 제공을 판단하지 않으며 상세 집주소를 사이트에 입력하게 하지 않는다.
- 결과 행에는 이름, 무슨 일을 돕는지, 이용 방식, 지역 확인 상태, 핵심 조건 요약, 주 행동을 표시한다. 상세에는 대상/제외 범위·비용 단위·최소량/추가비·공식 확인 경로·OS별 링크를 둔다.
- 대표 상세의 정보 순서: `언제 쓰는지 → 무엇이 필요한지 → 비용/조건을 어디서 확인하는지 → 공식 이동`. 구매가 필요한 상황은 상품으로, 이미 가진 물건의 관리 질문은 관리 정보로 연결한다.
- 주 행동은 `수거 조건 확인` 등 도착 목적에 맞춘다. 웹 페이지와 iPhone/Android 설치 링크를 구분하고 자동 설치/자동 앱 전환을 강제하지 않는다. 확인하지 않은 세부 화면 도착을 약속하지 않는다.
- 작은 화면은 한 열, 큰 화면은 읽기 쉬운 목록과 선택 상세를 제안한다. 목록에는 짧은 설명을 두고 긴 설명은 상세에서 읽는다. 실제 앱 로고가 없으면 이름과 기존 아이콘을 사용하고 엉뚱한 상품 사진으로 대체하지 않는다.
- 저장은 기존 상품 ID/만료 정책을 보존하고 `상품/장소/서비스` 종류와 ID를 구분한다. 저장 상태를 상품의 구매/보유 상태와 혼동하지 않는다. 복귀·저장 검증 전 완료로 표시하지 않는다.

기존 두 공식 사이트/앱 원장과 발견 큐를 stable ID/공식 도메인/제공자/앱 ID로 대조한다. 확인된 중복만 묶고 별칭·옛 이름·다른 기능·제휴 관계는 구분한다. 한 제공자의 여러 기능과 iOS/Android를 별도 업체 수로 세지 않는다.

| 단위 | 필수 내용 | 처리 |
|---|---|---|
| 제공 서비스 | ID·이름/별칭·운영자·고객용 여부·공식 경로 | 실제 이용자용 등록을 확인; 기사/파트너 앱 구분 |

B1~B4가 제품 적용까지 남은 네 작업 묶음이고 B5는 공개 단계다. B2와 B3는 일부 확인 자료부터 겹쳐 진행할 수 있지만 데이터 계약과 파일 담당을 먼저 고정한다. 단순 항목 수가 아닌 각 묶음의 완료 조건으로 진척을 보고한다.

대표 3흐름은 (1) 세탁세제 선택→건조/소재 차이→상품 링크, (2) 이불 관리→근처 빨래방/수거 세탁→공식 조건 확인→복귀, (3) 음식물 처리→구별 공식 안내/수거 조건→외부 이동이다. 브랜드 수를 맞추기 위해 용도가 다른 후보를 끼우지 않는다. 이후 전체 목록을 줄이지 않고 같은 계약으로 확장한다.

### 작업량과 토큰을 줄이는 방식

- 매 작업은 이 절과 상태/해당 큐만 읽고 원문 62,790개나 모든 문서를 다시 넣지 않는다. 근거가 애매한 ID만 원문으로 돌아간다.
- 수집은 `대상 발견→공식 기능 확인→필드 추출→검사`로 나눠 같은 URL/앱 ID의 성공 응답을 재사용한다. 비용/지원 변경이나 실패 항목만 재확인한다. 자동 추출 실패를 근거 없이 반복하지 않는다.
- 새 서비스는 한 레코드 계약으로 작성한다. 기존 제공자·필드 출처가 있으면 이어 채우며 iOS/Android/웹을 별도 조사 프로젝트로 중복 실행하지 않는다.
- 이름·ID·URL·필수값·합계·분류 누락·오래된 확인일은 스크립트로 검사한다. 기능 동일성·제품 적합성·화면 이해도만 모델/사람 판단에 남긴다.
- 모델 배분 제안은 설계/모호한 관계 판단에 Sol High, 계약 확정 후 구현에 Sol Medium, 형식이 고정된 추출/분류에 Luna Low/Medium이다. 자동 모델 전환을 구현했다는 의미가 아니며 경량 모델 출력도 같은 검사를 통과해야 한다.
- 전체 설계를 품목마다 반복하지 않는다. 대표 사례 세 개에서 조건과 공통 화면을 확인한 뒤 동일 구성과 검사로 나머지 범위를 적용한다. 범위 추가는 큐에 넣고 계약 변경이 필요한지 판단한다.

### 성과 판단

문제 검색 결과 존재 비율·0건 비율·상세 열기·공식 이동·저장 후 재열기를 구분한다. 이벤트 제안은 `service_search`, `service_detail_open`, `service_link_click`, `service_save`, `service_reopen`이며 현재 구현/발화 완료 상태가 아니다. 원문 검색어·상세 주소·개인 정보는 이벤트에 보내지 않는다. 결과 수/목적 ID/링크 플랫폼/발화 위치 같은 제한된 값으로 계측한다.

상품 구매처 클릭과 서비스 이동은 각각 집계한다. 외부 예약/구매 완료는 제휴 결과 등 실제 근거가 없으면 모른다. 대화 %를 앱 인기순이나 예산 배분 비율로 옮기지 않으며 체류시간 증가만으로 성공을 판정하지 않는다.
