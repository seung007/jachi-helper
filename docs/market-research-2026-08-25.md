# 자취도우미 1차 시장 데이터 수집 노트

작성일: 2026-08-25
목적: 기능을 늘리기 전에, `첫 자취 준비 -> 필요한 물품 결정` 흐름에 실제 수요와 제품 공백이 있는지 확인한다.

## 읽는 법

- **확인됨**: 원문을 열어 확인한 공개 출처의 사실
- **추론**: 확인된 사실에서 이 제품에 대해 도출한 해석. 사실 자체가 아니다.
- **미확인**: 아직 데이터가 없거나, 이 조사만으로는 답할 수 없는 질문

이 문서는 방향을 확정하는 문서가 아니다. 다음 사용자 검증에서 틀릴 수 있는 가정을 보존하는 작업 기록이다.

## 3. 현재까지 가능한 결론

### 확인된 범위

1. 1인 가구와 임차 생활은 충분히 큰 생활 맥락이다.
2. 이사·청소·상품 구매는 각각 강한 기존 대안이 있다.
3. 따라서 첫 기능의 경쟁 대상은 "모든 생활 서비스를 한곳에"가 아니라, 사용자가 이미 가진 정보 사이에서 **다음 결정을 빠르게 내리는 경험**이어야 한다.

### 아직 결론 내리면 안 되는 범위

1. 체크리스트 기반 구매 계획이 사용자가 반복 방문할 만큼 유용한가.
2. 어떤 품목과 조건이 가장 자주 선택되거나 제외되는가.
3. 예산 계산이 구매 결정을 실제로 바꾸는가.
4. 사용자에게 더 중요한 것은 가격, 배송, 품질, 공간, 향 민감도, 보유 여부 중 무엇인가.
5. 제휴 링크나 상품 데이터 연동이 전환을 높이는가.

위 다섯 항목은 현재 공개 통계나 검색량만으로 답할 수 없다. 제품 사용 데이터와 짧은 인터뷰가 필요하다.

## 4. 검색 수요 데이터 수집 상태

### NAVER DataLab

`data/search-groups.json`에 아래 8개 검색 주제 그룹을 정의해 두었다.

`자취 준비`, `침구·욕실`, `주방`, `청소·세탁`, `운동·세탁`, `저자극·무향`, `수납·생활`, `안전`

수집 스크립트는 `scripts/fetch-naver-trends.mjs`이며, API Hub의 검색어 트렌드 API를 사용한다. API는 상대 검색량을 주제별로 제공하므로 **절대 검색 건수나 구매 전환율의 증거가 아니다.**

- 공식 API 문서: [NAVER API Hub 검색어 트렌드](https://api.ncloud-docs.com/docs/naver-api-hub-search-trend)
- 현재 장애: 등록한 키로 API가 `401 Authentication Failed`를 반환한다.
- 해석: 이번 1차 결론은 DataLab 결과에 의존하지 않는다. 인증 정보 재발급 또는 애플리케이션 권한 확인 뒤 동일 스크립트로 원본 JSON을 수집한다.

## 5. 가장 싼 다음 검증

### A. 제품 내 행동 데이터

초기 버전에서 익명 이벤트만 모은다. 상세 주소, 계약서, 개인식별정보는 받지 않는다.

| 이벤트 | 답하려는 질문 | 성공·실패 판단 예시 |
| --- | --- | --- |
| `checklist_started` | 첫 화면의 약속이 행동으로 이어지는가 | 방문 대비 시작률 |
| `condition_selected` | 어떤 조건이 실제로 필요한가 | 조건별 선택 분포 |
| `purchase_plan_viewed` | 결과 화면이 만들어질 가치가 있는가 | 시작 대비 결과 도달률 |
| `item_marked_needed / owned / later` | 품목 우선순위가 현실과 맞는가 | 품목별 결정 분포와 제외 사유 |
| `search_destination_opened` | 검색어·구매 기준이 다음 행동을 만들었는가 | 결과 대비 외부 검색 진입률 |
| `feedback_missing / unnecessary` | 추천이 빠뜨리거나 과하게 권한 것은 무엇인가 | 상위 누락·불필요 품목 |

### B. 15분 사용자 인터뷰 10명

대상은 최근 3개월 내 독립했거나 3개월 안에 입주 예정인 사람으로 제한한다. 성별이 아니라 실제 생활 조건을 묻는다.

1. 입주 준비 중 가장 최근에 검색한 것은 무엇이었나.
2. 결국 사지 않은 물건은 무엇이고, 왜 사지 않았나.
3. 이미 가진 물건과 새로 사야 할 물건을 어떻게 구분했나.
4. 검색부터 구매 결정까지 가장 오래 걸린 품목은 무엇이었나.
5. 예산을 적지 않았다면, 적지 않은 이유는 무엇이었나.
6. 결과가 어떤 형식이면 친구에게 공유하거나 다시 열어 볼 것 같은가.

인터뷰에서는 "이 서비스 좋죠?"를 묻지 않는다. 최근 실제 행동, 버린 선택지, 사용한 대안을 먼저 듣는다.

## 6. 이후 방향을 가르는 기준

| 관찰 결과 | 다음 방향 |
| --- | --- |
| 체크리스트 완료는 높지만 외부 검색 진입이 낮음 | 결과가 추상적이거나 구매 기준이 약하다. 품목 수를 늘리기보다 이유·조건·검색어를 고친다. |
| 특정 카테고리에서만 반복 결정이 발생 | 전체 자취 플랫폼보다 해당 카테고리의 깊은 결정 도구를 먼저 검증한다. |
| 사용자가 예산을 거의 입력하지 않음 | 긴 입력폼을 줄이고, 선택형 기본값과 "대략 얼마까지"만 남긴다. |
| "이미 있음"과 "나중"이 많이 선택됨 | 추천 개수 경쟁보다 제외와 보류를 잘 기록하고 다시 꺼내는 기능을 우선한다. |
| 외부 검색 진입은 높지만 피드백이 나쁨 | 검색어 또는 상품 기준이 맞지 않는다. 실시간 상품 순위·가격 기능은 아직 추가하지 않는다. |

## 7. 보류 원칙

- 실제 상품 가격, 재고, 배송, 성능, 판매 순위는 공식·제휴 데이터가 생기기 전까지 추천 근거로 표시하지 않는다.
- RAG/LLM은 데이터가 확보된 뒤 근거 설명과 추가 질문에 사용한다. 기본 우선순위는 사용자가 누른 조건을 해석하는 규칙으로 시작한다.
- 제휴와 중개는 구매 계획의 유용성이 검증된 뒤에만 검토한다.
